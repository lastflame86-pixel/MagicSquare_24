- 맥락: 알고리즘·배열·테스트·책임 분리(생성/검증/출력).

## Turn 3 — User (STEP 2)

```text
--------------------------------------------
STEP 2 — Why #1
--------------------------------------------
Q: 왜 마방진을 완성해야 하는가?
A를 가정하여 답하고, 그 답에서 드러나는 불편함 또는 구조적 문제를 분석하십시오.
```

### Turn 3 — Assistant (요약)

**가정 A:** 사용자가 신뢰할 수 있는 유효 4×4 격자를 프로그램이 대신 완성·부담 이전.

**구조적 문제 6가지:**

1. 완성 ≠ 생성 ≠ 검증  
2. 다중 해 → 오라클(특정 배열 vs 규칙) 공백  
3. 신뢰 근거·실패 설명 부재  
4. UI·형식 부담 누락  
5. 검증만 필요한 니즈와 충돌  
6. 실패·부분 상태·DoD 공백

| 검증 자동화 | 오라클 기계 적용, 대량·CI |
| 오류 방지 | 전수 검사; 명세+테스트 필요 |
| 규칙 기반 사고 | 규칙 명문화·테스트 연결 |

**종합:** 품질·학습·재현성 고정. Why #1+2 → 검증·(필요 시) 생성의 규칙 고정 과정.

### Turn 5 — Assistant (요약)

- **TDD 이유:** 불변 I1~I7을 테스트로 먼저 통제.
- **통제:** 판정·부정·회귀·책임 분리·(선택) 결정성.
- **불변:** 크기·집합·행·열·대각 합; 특정 배치는 불변 아님.
- **입출력:** Given/Then = 계약; 첫 실패 테스트로 검증 vs 생성 갈림.

```text
−	구현 설계는 하지 마십시오.
−	코드 언급 금지.
−	알고리즘 설명 금지.
−	구조화된 Markdown으로 작성하십시오.
```

### Turn 6 — Assistant (요약)

1. **표면:** “마방진 만드는 프로그램” — 모호·관측 불가.  
2. **개선:** 규칙 판정 + 선택적 산출 + 자동·반복 검증.  
3. **Invariant:** S·V·M·P 계층.  
4. **사고:** 규칙 분해, 오라클, 계약, 회귀, 문제 정의 비판.
