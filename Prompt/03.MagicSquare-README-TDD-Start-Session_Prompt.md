## 2. PRD 요약 (PRD Summary)

### 2.1 제품 문제 정의

제품 문제는 “아무 마방진이나 만든다”가 아니라:

> **빈칸 2개가 있는 4×4 격자**에 누락 숫자 2개를 배치하여 **검증 가능한 불변식**을 만족시키고, **고정 출력 계약**으로 좌표·값을 반환한다.

### 2.2 고정 입력 계약

| 항목 | 규칙 |
|------|------|
| 격자 | `int[][]`, 정확히 4×4 |
| 빈칸 | 값 `0`, **정확히 2개** |
| 허용 값 | `0` 또는 `1..16` |
| 중복 | `0`을 제외한 `1..16` 중복 금지 |
| 첫 번째 빈칸 | **row-major** 스캔(행 우선)에서 처음 발견되는 `0` |
| 두 번째 빈칸 | 동일 스캔에서 두 번째 `0` |

### 2.3 고정 출력 계약

| 항목 | 규칙 |
|------|------|
| 성공 형식 | `int[6]` = `[r1, c1, n1, r2, c2, n2]` |
| 좌표 | **1-index** (`r`, `c` 각각 `1..4`) |
| `n1`, `n2` | 배치된 누락 숫자 (Attempt 규칙에 따름) |
| 변환 | `(r1,c1) = (row0+1, col0+1)` (내부 0-index → 1-index) |

### 2.4 Solver 시도 순서

| Attempt | 배치 규칙 | 성공 시 반환 |
|---------|-----------|--------------|
| **1 (small-first)** | `small` → 첫 빈칸, `large` → 둘째 빈칸 | `[r1,c1,small,r2,c2,large]` |
| **2 (reverse)** | Attempt 1 실패 시: `large` → 첫 빈칸, `small` → 둘째 빈칸 | `[r1,c1,large,r2,c2,small]` |
| **실패** | 두 Attempt 모두 마방진 검증 실패 | `ERR-SOL-001`, `SolveStatus.UNSOLVABLE` |

### 2.5 기능 요구사항 (FR) 매핑

| FR | 기능 | Layer |
|----|------|-------|
| **FR-01** | 입력 검증 | Boundary |
| **FR-02** | 빈칸 좌표 탐색 (row-major) | Domain |
| **FR-03** | 누락 숫자 탐색 (오름차순 쌍) | Domain |
| **FR-04** | 마방진 검증 (행·열·대각선 합 34) | Domain |
| **FR-05** | 두 조합 Solver + 결과 포맷 | Domain + Boundary |

|------|------|-------------|

| 빈칸 ≠ 2 | ERR-BND-002 | **0회** |

## 3. TDD 흐름 (TDD Flow)

### 3.1 Dual-Track 개요

```text
Track A (Boundary)          Track B (Domain)
─────────────────          ─────────────────
입력 검증 RED               빈칸·누락·검증·Solver RED
출력 형식 RED               small-first / reverse RED
Domain 0-call RED           unsolvable RED
        │                           │
        └───────────┬───────────────┘
                    ▼
            Integration RED (E2E)
                    ▼
              REFACTOR (구조만)
```

### 3.2 Red → Green → Refactor 규칙

| 단계 | 규칙 |
|------|------|
| **RED** | 실패하는 테스트를 **먼저** 작성; pytest로 **FAILED** 확인 후에만 구현 |
| **GREEN** | 현재 RED **1건**만 통과시키는 **최소** 코드 추가 |
| **REFACTOR** | 현재 RED Green + P0 회귀 통과 후에만 구조 개선 |

**금지:**

- RED 2건 이상 동시 Green
- Domain 전부 구현 후 Boundary 부착
- assert 완화·삭제·`@pytest.mark.skip`/`xfail`로 Red 제거
- Boundary 실패 시 Domain 호출

### 3.3 권장 RED 순서

1. **Track 0:** DEC-003 픽스처 확정 (선행 권장)
2. **Track A:** RED-BND-001 → 002 → 003 → 004 → ISO-001 → OUT-001
3. **Track B:** RED-DOM-BLK-001 → MISS-001 → VAL-001 → SOL-001 → SOL-002 → SOL-003
4. **Integration:** RED-INT-001 (E2E), NFR 회귀
5. **Refactor:** RuleCatalog 상수 일원화, Orchestrator 정리

### 3.4 테스트 명명·구조 (계획)

| 항목 | 규칙 |
|------|------|
| 파일 | `test_<REDID>_<rule>_<behavior>.py` |
| 함수 | `test_RED01_given_3x4_when_parse_then_rejected_with_S1` 형식 |
| 패턴 | AAA (Arrange-Act-Assert) |
| 픽스처 | `tests/fixtures/grids/` JSON |
| Track A 경로 | `tests/unit/boundary/` |
| Track B 경로 | `tests/unit/entity/` 또는 `tests/unit/domain/` (ECB 정렬) |

## 4. 방법론 (Methodology)

### 4.1 Concept → Code 추적성

모든 구현 작업은 다음 체인으로 추적 가능해야 합니다:

```text
Concept / Invariant
    → Business Rule (BR-xx)
        → Feature (FR-xx)
            → Acceptance Criteria (AC-xx)
                → RED Test ID
                    → Component
```

### 4.2 Track A / Track B 병렬 진행

| Track | 초점 | 대표 AC |
|-------|------|---------|
| **A — Boundary** | IN/OUT 계약, ERR-BND-*, Domain 격리 | AC-BND-001~005, AC-BND-ISO-01 |
| **B — Domain** | 불변식 로직, Solver Attempt | AC-DOM-002~005, AC-SOL-001 |

**운영 원칙:**

- Boundary RED와 Domain RED는 **별도 테스트 모듈**로 분리
- 각 RED는 독립적으로 Red → Green → (필요 시 Refactor) 완료
- Integration RED는 양 Track 최소 Green 이후

### 4.3 오라클 원칙

- **규칙 집합**이 오라클이며, **특정 16칸 정답 배열 전체 일치**는 금지
- 마방 상수 `34`, 격자 크기 `4`, 값 범위 `1..16`은 **명명 상수**(`MAGIC_SUM`, `GRID_SIZE` 등)로 참조
- 유효 격자는 **2종 이상**으로 회귀 검증 (Validator Phase; Solver Phase는 DATA ID별)

### 4.4 금지 패턴 (요약)

| 금지 | 대안 |
|------|------|
| `print(` | `logging` 또는 pytest 실패 메시지 |
| `except:` / `except Exception: pass` | 명시적 예외 + 도메인 오류 변환 |
| 하드코딩 34·16칸 전역 배열 | RuleCatalog·entity/constants |
| `@pytest.mark.skip`/`xfail` (Red 제거 목적) | 구현 또는 Then 수정 |
