## Given–When–Then

| 구분 | 내용 |
|------|------|
| **입력 예시** | `matrix = null` (`grid = None`) |
| **When** | `UIBoundary.solve(matrix)` 또는 `InputValidator.validate(matrix)` 호출 |
| **기대 출력** | `{ "type": "ERROR", "error": { "code": "E003", "message": "INVALID_MATRIX_NULL: matrix must not be null" } }` |
| **부가 기대** | `SolvePartialMagicSquare.execute` (Domain resolver) **0회** 호출 |

> **PRD SSOT 참고:** `null` 입력은 **E003**이다. 크기 위반(3×4 등)은 **E001** (`INVALID_MATRIX_SIZE: expected 4x4`)이며, 프롬프트 예시의 `INVALID_SIZE`는 E001 크기 위반에 해당한다. `grid = None` 앵커 케이스는 E003이 정확한 기대값이다.

---

## 선택 이유 (2줄)

1. FR-01 Processing Rule 6에 따라 검증 순서가 **null → size → empty count → value range → duplicate**이므로, AC-FR01-01은 FR-01 Acceptance Criteria 중 **가장 선행하는 입력 유효성 조건**이다 (AC-FR01-08에서도 null 검증 선행을 명시).
2. `InputValidator` 단위 테스트(U-IN-01)로 **Boundary 비즈니스 로직**(null → E003 반환)을 직접 검증하고, `UIBoundary` + mock resolver(U-FLOW-02)로 **Domain 진입점 호출 0회 격리**를 동시에 검증할 수 있어 Dual-Track TDD Track A의 첫 RED에 적합하다.
